**The only supported real model is Qwen3.6-35B-A3B.** The CLI, demo, and default launcher all select this model, with default weights set to `models/qwen3.6-35b-a3b-8bit-mlx`. Checkpoints for 5bit and 8bit of the same model continue to be supported; loaders, downloaders, and launch entries for Qwen2.5 3B/7B and TinyStories have been removed. `synthetic-v1` is used only for RPC tests that do not load weights.

The product executes inference via self-written C# / Metal / CUDA paths, without calling Python, Transformers, MLX, llama.cpp, or external model services. Python is used only for downloading, independent references, and acceptance scripts.

## Direct Launch

The dual-machine experiment entry has been implemented on the `codex/split-prefill` branch ([PR #8](https://github.com/LittleLittleCloud/Infer.NET/pull/8)): 4090 resides before the 20 layer, and after execution on Mac, the 20 layer takes over decoding upon receiving the complete state. 8bit weights, **FP32 KV diagnostic mode**'s 17/8, 61/32, and dual-end Native AOT verification have passed; the BF16 target path has not yet met strict numerical thresholds, with current input plus output totaling at most 2K, and TUI integration is not yet available. After preparing environments and weights on both ends, execute on Mac:

```sh
python3 scripts/split/run-dual.py --native --verify --kv fp32
```

For complete prerequisites, builds, evidence, and failure records, see [Dual-Machine Experiment Instructions](docs/SPLIT-PREFILL.md). This is not a performance acceptance for 128K.

On this M5 Pro 48GB, double-click **`DeepInfer.command`**, or:

```sh
./scripts/mvp.sh
```

For first-time use, download the fixed-version 8bit weights first:

```sh
python3 scripts/download-qwen36-mlx.py --bits 8
./scripts/mvp.sh
```

The download environment requires `huggingface-hub`. The launcher starts a coordinator, a Qwen3.6 Metal Worker, and a terminal interface; press Ctrl+C to exit and clean up child processes. Use `DEEPINFER_BASE_PORT=5500` to override the default port 5100–5101, or use `DEEPINFER_WEIGHTS=models/qwen3.6-35b-a3b-5bit-mlx` to explicitly select the 5bit weights for this model. When using existing original artifacts, use the programs under `artifacts/`; otherwise, build the hosted version. After modifying source code, please rebuild or publish artifacts.

`DeepInferMoE.command` is retained as the M5 tuning entry for the same model and also uses default 8bit weights. Explicitly adding `--workers` will load an additional complete model copy; confirm memory capacity first.

## Qwen3.6-35B-A3B: Self-written Metal / C# Engine

**8bit performance target v1 is fixed**: 128K without prefix cache, dual-machine end-to-end prefill final target **2000 token/s**, 128K + 4096 output for the entire request **≤ 180 seconds**, continuous decode **≥ 37 token/s**. Phase acceptance lines are 1600 token/s / 200 seconds; these are all targets to be implemented. Model, timing, re-measurement, correctness, and memory thresholds are detailed in [Performance Acceptance Specification](docs/QWEN36-8BIT-TARGETS.md).

**8bit new baseline (independent artifact)**: Self-written Metal has completed support for 8bit weights and actual model verification. For M5 Pro 48GB, AC / High Power, steady-state prefill for 8K / 32K / 128K inputs is **3.467 / 17.743 / 135.966 seconds**, decoding **66.34 / 60.51 / 37.52 token/s**. **128K + 4096 output** ran completely using 512 chunking: prefill **164.157 seconds**, continuous decode **38.95 token/s**. Splitting the final vocabulary projection reduces the resident peak per submission; long outputs still require shrinking the workspace. The entire machine does experience paging, so it cannot be considered free of memory pressure. Layer-by-layer verification, 68 item unit tests, and 4 item long-request RPC acceptance have passed; reproduction, failure records, memory limits for 8bit, and 20/20 dual-machine capacity/benefit estimates are detailed in [8bit Verification Report](docs/QWEN36-8BIT.md). The current launcher defaults to using 8bit; the following retains previous 5bit measurements.

**M5 tuning configuration (historical 5bit measurements)**: adaptive expert tail blocks of 16/32/64, fused gate/up matrix multiplication, and direct DeltaNet matrix reads. On AC / High Power, using the same binary and precision, each tier had three warmups and three measured runs. 8K prefill was **3.468 → 3.353 seconds (3.32% reduction)**; 32K was **17.850 → 17.344 seconds (2.83% reduction)**. All 128 output tokens matched in both A/B tiers, with unchanged GPU allocations and submission counts. Fresh MLX controls took **2.967 / 14.701 seconds**, so prefill remained **12.99% / 17.98%** slower and had not reached parity; decode in this round was **84.76 / 74.88 token/s**. All 287 Metal checks, 68 unit tests, 25 RPC checks, and 4 real-model checks passed. `DeepInferMoE.command` selects the new configuration; see [Implementation and complete evidence](docs/PREFILL-EXPERT-DELTA.md). Historical rounds remain below, with their conditions kept separate.

Previous expert intermediate layout experiments: Implemented gate/up direct output of the down BF16 layout required, 8K same-round prefill time reduced by approximately **1.4%**; 32K initial test and supplementary tests were slower by approximately **1.1% / 0.5%**, thus retaining the original default path. Dequantization double buffering was slower by approximately **7.1%** in 8K, so it was not enabled. Precision and outputs remain unchanged; see [Implementation, High Power Actual Measurements and Verification](docs/EXPERT-FLOW.md).

Double-click **`DeepInferMoE.command`**, or run `./scripts/mvp.sh`. First use `python3 scripts/download-qwen36-mlx.py --bits 8` to obtain fixed-version quantized weights; the downloader's Python environment requires `huggingface-hub`, but the product runtime does not require Python.

Supports 5-bit or 8-bit/group64 affine weights, 8-bit router, 256 expert Top-8, shared experts, 30 layer Gated DeltaNet, and 10 layer gated full attention checkpoints for this series. Default full forward pass is completed in the self-written Metal GPU executor, including quantized GEMV, expert SwiGLU, normalization, convolution, RoPE, two types of attention, routing, and argmax; C# handles tokenization, generation control, and RPC. FP32 activations, states, and accumulations. **No calls to MLX, llama.cpp, Ollama, or external model services.** `mlx` only appears in the checkpoint format/directory names being read.

**Previous Round M5 Configuration (Mixed Precision, Historical Measurements)**: Identical five-digit weights, identical inputs, fixed 128 outputs, one warm-up followed by three measurements. 8K prefill **3.734 → 3.491 seconds**, 32K **19.917 → 17.979 seconds**, time reduced by **6.5% / 9.7%** respectively; this round's MLX re-measurement is **2.962 / 14.666 seconds**, still not achieving prefill parity. 8K decoding **84.70 / 84.37 token/s (self-written / MLX)**, 32K is **74.84 / 71.46**. Optimized expert chunking and thread counts, attention register usage, maintaining the previous version's precision boundaries; 68 unit items, 511 Metal items, 25 RPC items, and 4 real model acceptance passed. See [This Round's Implementation, Limitations, and Original Evidence](docs/PREFILL-TUNING.md). The following early measurements retain their respective configurations and must not be mixed.

**Subsequent Plug-in Verification**: Model-level prefill chunking is **2048**; 128 is the Attention query scheduling batch. 128/512/1024 per tier, each length fully warmed up three times then measured three times, 132 power supply observations are all AC, outputs consistent per token. Retaining 128, 8K/32K prefill mean **3.431 / 17.856 seconds**, decoding **86.13 / 74.90 token/s**. Expanding to 512/1024 is slightly slower in 8K, and only faster by approximately 1.2%/0.8% in 32K, occupying an additional 390/910 MiB of 32K buffer respectively, thus defaulting to retaining 128. This round did not re-measure MLX, so no new parity conclusions can be drawn against the previous historical data. See [Chunking Levels, AC Re-measurement, and Evidence](docs/ATTENTION-BATCH.md).

The 2026-10-21 short-input retest on this M5 Pro 20-core GPU / 48GB machine (then using 32-token chunks) reduced worker first-token latency from **217.1 → 92.3 ms**, a **57.5%** reduction, while maintaining decode at **96.60 token/s**. With the same 24-token input and 128-token output, one warmup and three measured runs per configuration gave MLX **FP32 first-token latency of 93.9 ms / decode of 85.27 token/s**; default MLX **BF16 gave 87.3 ms / 90.59 token/s**. Short-input first-token latency was approximately at parity with the same-precision FP32 reference; BF16 remained about 5 ms faster. All 128 output tokens exactly matched MLX FP32. Weights remained compactly stored, with FP32 activations, states, and accumulation; precision was not reduced and answers were not cached. Each decode forward used **675 kernels / 1 submission and wait**; the complete 24-token prefill also needed only one submission.

## Pi + HumanEval wall-time harness

`scripts/benchmark-pi-humaneval.py` measures the **real Pi CLI** using
`infernet/qwen3.6-35b-a3b`, serially, with standard read/write/bash/edit tools.
It never starts, restarts, or deploys a server. Python 3.9+ and a separately
installed Pi are required; no Python packages are needed.

**Dataset pin:** official [OpenAI HumanEval](https://github.com/openai/human-eval),
revision `b9453e8f1865df0a0057a1383767caa400acfbcf`,
[`data/HumanEval.jsonl.gz`](https://raw.githubusercontent.com/openai/human-eval/b9453e8f1865df0a0057a1383767caa400acfbcf/data/HumanEval.jsonl.gz),
compressed-file SHA-256
`b796127e635a67f93fb35c04f4cb03cf06f38c8072ee7cee8833d7bee06979ef`.
The runner verifies the digest and all 164 IDs before running any task. Use
`--dataset /absolute/path/HumanEval.jsonl.gz` for an offline copy of those exact
bytes. The dataset is not bundled; its upstream MIT license applies.
Only task IDs and prompts are retained after loading; tests and reference
solutions are never supplied in Pi's prompt or workspace.

### Reproduce

Use a disposable environment with only the intended local Infer.NET endpoint
reachable. Pi's bash tool runs generated commands: **a fresh workspace is not
a security sandbox**. Do not run this with unrelated credentials, private
files, or a local HumanEval checkout accessible to the agent. No official
evaluator or generated solution is executed by the harness; Pi itself may run
commands or syntax checks while solving the task.

The Pi CLI interface was checked against upstream
[`136b87e8a7f5a3e5186de0289523ba327dc592fc`](https://github.com/badlogic/pi-mono/tree/136b87e8a7f5a3e5186de0289523ba327dc592fc/packages/coding-agent)
(package version 1.4.0). Install a Pi release supporting the recorded flags,
including `--no-context-files` and `--no-approve`; unsupported flags are task
failures, not grounds to silently weaken isolation. Keep the **same exact Pi
version** for baseline and candidate. `--pi /absolute/path/to/pi` selects the
executable. On Windows, where npm normally installs a `.cmd` wrapper, pass
`--pi C:\absolute\npm\node_modules\@earendil-works\pi-coding-agent\dist\cli.js`
(use the actual installed package path). The harness invokes that entry point
with `node` from PATH, without shell quoting of prompts. `.cmd`/`.bat` wrappers
are rejected. Bash must also be available for Pi's bash tool.

Start and validate the authenticated local server separately using its normal
deployment instructions. Its OpenAI-compatible chat endpoint must support
tool calls. Supply the existing token **file path**, never a token in command
arguments. The runner does not read your normal Pi config: it generates a
fresh `models.json` for the loopback endpoint using the
`$INFERNET_BENCH_TOKEN` key reference and explicit HTTP authentication. It disables
discovery of extensions/MCP/skills/context files,
disables retry/compaction, uses `--thinking off`, and uses `--no-session`.
Each task gets a new temporary workspace, home, and agent directory, removed
after collection. The child environment is restricted, but the local API
token is necessarily available to Pi (and hence its tools).

The generated `infernet/qwen3.6-35b-a3b` model uses `openai-completions` with
explicit endpoint compatibility: `maxTokensField="max_tokens"`,
`supportsDeveloperRole=false`, `supportsReasoningEffort=false`, and
`supportsStore=false`. The current Infer.NET endpoint requires `max_tokens`
rather than `max_completion_tokens`, does not support the developer role, and
rejects `reasoning_effort` and `store` parameters (including `store=false`).
These settings prevent Pi from sending unsupported parameters; they match the
working Pi model configuration without reading or modifying your normal config.
The offline fixture checks these fields in each task's generated `models.json`.

From the repository root (replace paths/build labels with verified local values):

```sh
python3 scripts/benchmark-pi-humaneval.py \
  --cohort pilot --seed 0 --timeout 600 \
  --endpoint http://127.0.0.1:5200 --token-file /absolute/private/token \
  --endpoint-build VERIFIED_BUILD --model-revision VERIFIED_MODEL_REVISION \
  --output artifacts/pi-humaneval/baseline-pilot

# Run only after reviewing pilot evidence; use a fresh directory every time:
python3 scripts/benchmark-pi-humaneval.py \
  --cohort cohort --seed 0 --timeout 600 \
  --token-file /absolute/private/token --output artifacts/pi-humaneval/baseline-20

python3 scripts/benchmark-pi-humaneval.py \
  --cohort full --seed 0 --timeout 600 \
  --token-file /absolute/private/token --output artifacts/pi-humaneval/baseline-164

# Explicit IDs override cohort selection:
python3 scripts/benchmark-pi-humaneval.py \
  --ids HumanEval/0,HumanEval/1 --timeout 600 \
  --token-file /absolute/private/token --output artifacts/pi-humaneval/explicit

# Offline fixtures, also run in CI; no Pi, model, network, or GPU:
python3 scripts/test-pi-humaneval.py
```

Selection sorts IDs by SHA-256 of UTF-8 `SEED:HumanEval/N`, ascending;
`pilot` takes 5, `cohort` takes 20, and `full` takes 164. Thus the pilot is
contained in the fixed 20-task cohort for the same seed. Explicit IDs preserve
the supplied order. The seed controls **selection only**, not server sampling.
Defaults are a 32,768-token context declaration and 4,096 output tokens per
request; set `--context-window` / `--max-tokens` to the real endpoint limits.
Do not change them between comparisons. Build/model revision fields default
to `null`: supply verified non-secret provenance when available, not guesses.

### Evidence and interpretation

The new output directory contains:

- `manifest.json`: exact source/digest, ordered IDs, seed, Pi version,
  endpoint/build/model revision, limits, timeout, and harness digest.
- `tasks.jsonl`: one record per attempted task, including failures/timeouts;
  prompt hashes (both dataset and complete user prompt), exact Pi command,
  version/provider/model, UTC start/end and monotonic process wall time,
  return/finish status, authoritative assistant-message usage, request and
  turn timings, tool lifecycle records, solution hash and syntax status.
- `HumanEval-N/events.jsonl`: raw Pi event objects wrapped with harness-observed
  monotonic receive offsets; stderr and malformed lines are retained separately.
  API credentials are redacted before writing, including JSON-escaped values.
  Streaming usage snapshots are **not** summed: only assistant `message_end`
  usage is counted, once per response, not duplicate `turn_end`/`agent_end` data.
- `HumanEval-N/solution.py`: collected implementation, never evaluated. Syntax
  means only `ast.parse` succeeded, not that the answer is correct. Original
  bytes are hashed; if credentials are redacted, `stored_solution_sha256`
  records the different stored bytes.
- `summary.json`: task/completion/syntax/timeout/error counts, median,
  nearest-rank p90 and total task wall time, token totals, request count and
  observed request-time statistics. All failed/timed-out tasks remain in the
  wall-time denominator. Partial usage is retained when reported; missing
  usage is not estimated. In-flight requests lacking `message_end` have no
  completed-request usage/duration record. Nonzero exit indicates task failure.

Wall time runs from Pi process launch through exit/timeout cleanup, including
startup, model requests, tools, and orchestration; dataset download, directory
setup, and the harness's post-run syntax parsing are outside that interval.
`observed_seconds` measures assistant `message_start` to `message_end` receipt;
`duration_ms` is Pi's optional reported request duration. Turn duration includes
tools. Neither is server-only prefill/decode telemetry or GPU kernel timing.
Older Pi streams may omit reported durations and `agent_settled`; the parser
also accepts terminal `agent_end` with a final successful assistant response.
Windows runs each capture in a private, kill-on-close Job Object. A gated Python
launcher starts Pi only after job assignment succeeds; Pi and its descendants
are terminated even if Pi exits first. Breakaway is not enabled. Cleanup waits
for the job to empty and reaps the launcher, using bounded three-second waits;
cleanup errors are reported as `cleanup_failed:<exception type>`, not suppressed.
Windows termination is asynchronous: zero active job processes is not a barrier
for every retained process handle to signal. The Windows regression verifies
membership of the launcher, Pi stand-in, and descendant in the exact capture job
(and excludes an unrelated process), then requires their exit signals within a
shared one-second teardown deadline after capture, with total elapsed time under
five seconds. It covers both a sleeping Pi and Pi exiting before its descendant.
Launcher startup and all cleanup remain included in wall time. Windows hosts
whose existing job restrictions prevent nested job assignment fail before Pi
starts; there is no uncontained fallback. POSIX uses a process group; descendants
that deliberately escape it still require external disposable-environment
cleanup. Neither mechanism contains work delegated to an existing external
service. Unrelated processes/services are never stopped.

**This is not HumanEval pass@1, even for the full run. A subset is not a standard
leaderboard score.** No correctness claims are made without the official
evaluator in an appropriate isolated execution environment. No live-model
results are asserted by these fixtures. Before publication, the orchestrator
must review the five-task pilot, then run baseline/candidate 20-task cohorts
with matched IDs/order, Pi version, harness digest, token/context limits,
model revision/precision, server state/cache policy, hardware, power and load.
Keep failed evidence and publish only validated results.

`deepinfer` can be replaced with the path to the built program, or `dotnet run --project src/DeepInfer.Host -c Release --`. Run each role independently:

```sh
deepinfer coordinator
deepinfer worker --id qwen-mac --listen http://127.0.0.1:5101 --backend metal \
  --weights models/qwen3.6-35b-a3b-8bit-mlx --model qwen3.6-35b-a3b

```

Worker only loads `mlx-qwen36-affine` format, tokenizer defaults to `tokenizer.json` in the weight directory. Metal executes the full model, CUDA frontend connects via the persistent dual-machine service below. CPU numeric operators are retained for verification, no longer providing a CPU model backend. Each real model Worker capacity is fixed at 1; workers without weights only probe devices.

Single-turn interface uses non-thinking chat template, greedy decoding, independent request state; structured multi-turn and streaming interfaces see [Chat API](docs/CHAT-API.md). Input and output share 262, 144 token window, actual available capacity depends on memory; configuration upper limit does not equal passing all length acceptance.

## Benchmarks and Limitations

```sh
deepinfer bench --requests 3 --warmup 1 --max-tokens 128 --output artifacts/benchmark-qwen36.json
```

`timings.prefillMs` measures prompt forward; `timings.decodeTokensPerSecond` measures N−1 generation intervals between the first and last output token. `tokensPerSecond` includes prefill and RPC. Internal first-token time for non-streaming interfaces cannot be treated as network-visible TTFT.

Service does not silently fall back to other models or backends. Cross-machine access must explicitly enable `--allow-remote` and configure unified token; use trusted private network/VPN or TLS termination. Complete 128K performance and resource thresholds still accept according to [Fixed Specification](docs/QWEN36-8BIT-TARGETS.md).

Apache-2.0 license and fixed version summary for Qwen3.6 checkpoints are retained in the corresponding model directory, weights are not committed to Git. Only text path for this model is supported; image, MTP, YaRN, GGUF, and general rank communication are not yet implemented. Pure simulation tests explicitly use `demo --backend simulation` or `infer --backend simulation --model synthetic-v1`.

M5 tuning entry selects hybrid GEMM, packed experts, and BF16 attention. Precision boundaries and historical measurements see [BF16 Metal](docs/BF16-METAL.md) and [Tuning Records](docs/PREFILL-TUNING.md).

## Persistent 8bit deployment

The `split-serve` / `split-agent` commands keep Metal and CUDA weights loaded across requests, warm the complete Mac graph before readiness, reset request state, and use pinned mutual TLS for cross-host state transfer. The local coordinator exposes both complete and streamed responses; CLI and TUI share it. Current limits: affine8 weights, FP32 KV, 2048 total tokens and 256 output tokens, one active request plus a bounded queue. BF16/128K performance acceptance remains open.

See [deployment instructions](docs/DEPLOYMENT.md) for private configuration, Native AOT packaging, Mac LaunchAgents, Windows Service installation, upgrade/rollback and real-model acceptance. Windows Service installation requires administrator PowerShell; the foreground SSH runner is only for development.

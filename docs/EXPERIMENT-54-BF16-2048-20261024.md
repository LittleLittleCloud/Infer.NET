# Experiment 54: main versus CUDA BF16 GEMM + 2048-token outer chunk

Status: measured negative result; **do not adopt the candidate as the default**. This is an FP32-KV, Wi-Fi-LAN diagnostic, not the Q8-KV or 128K acceptance run.

## Fixed request: 8192 input, 128 output

One warmup and three formal requests per build, no prefix hit, fixed output length, same input SHA-256 `defa12f5be86a88aed8a25aa479ab1b17860a661ff364865708e121cac17206d`. Values are medians of the three formal requests. Stages overlap and **must not be added**.

| Metric | `main` | BF16 + 2048 | Candidate change |
|---|---:|---:|---:|
| Complete split prefill | 11.519 s | 12.944 s | **+12.4% time** |
| CUDA compute | 10.016 s | 6.521 s | **−34.9% time** |
| CUDA send/write | 9.804 s | 11.220 s | +14.4% time |
| CUDA stage wall | 11.482 s | 12.910 s | +12.4% time |
| Mac hidden wait | 0.634 s | 2.068 s | +1.434 s |
| Mac suffix compute | 10.293 s | 10.302 s | essentially unchanged |
| Decode | 60.04 tok/s | 60.28 tok/s | +0.4% |
| Client request wall | 13.645 s | 15.059 s | +10.4% time |

All three formal repetitions in each build produced a stable token sequence. The two builds produced different token hashes (`cb1c4d9d899d…` versus `16fee558254d…`), which is expected under changed arithmetic but is **not** a quality judgment. The BF16 path has not yet passed an independent same-precision long-prefix state/logit reference. The 2048 outer chunk computes much faster on CUDA but delays delivery of the first group of hidden states to Mac; the resulting loss of overlap dominates this fixed end-to-end request. The measured Wi-Fi transfer time adds uncertainty to the size of the regression, so a wired retest is needed before making a network-independent claim.

Because the candidate changes both precision and outer chunk size, this A/B cannot assign the CUDA-compute gain or complete-pipeline regression to either change alone.

## Pi HumanEval: fixed 20-task cohort

Official HumanEval dataset gzip SHA-256 `b796127e635a67f93fb35c04f4cb03cf06f38c8072ee7cee8833d7bee06979ef`, seed 0, Pi 1.4.0, 32768-token Pi context, 4096-token output cap. The same 20 task IDs are in both run manifests. Official assertions were **not** run: “completed” means Pi finished with a syntax-valid file, not HumanEval pass@1. Worker speeds use total input tokens divided by total worker prefill time, and total `N−1` decode intervals divided by total worker decode time.

| Metric | `main` | BF16 + 2048 | Candidate change |
|---|---:|---:|---:|
| Pi tasks completed | 20/20 | 20/20 | — |
| Model requests / captured worker metrics | 104 / 104 | 116 / 116 | +12 requests |
| Worker input / output tokens | 259,107 / 20,712 | 268,359 / 20,443 | different generated workload |
| Worker prefill | **570.26 tok/s** | **417.36 tok/s** | **−26.8%** |
| Worker decode | 66.94 tok/s | 67.09 tok/s | +0.2% |
| Pi total wall | 770.70 s | 954.63 s | +23.9% |

The first exact-`main` run completed 19/20 tasks and emitted no `INFERENCE_METRIC` lines because that source revision lacks the log. It remains in local evidence as a failed measurement attempt. A second exact-`main` run used read-only polling of the worker's `lastRequest` telemetry every 100 ms; its **104 captured records exactly match 104 Pi model requests**, with zero polling errors. Candidate telemetry independently matched 116/116 and its `INFERENCE_METRIC` log produced identical aggregate speeds. Decode duration for the polled `main` records was reconstructed from the worker's `N−1` interval count and reported decode rate. No Dashboard last-request snapshot or Pi wall time was substituted for missing per-request metrics.

Candidate Pi generated a different sequence of tool/model requests, so the 23.9% Pi wall increase is an application result rather than an isolated CUDA-kernel effect. The fixed-input result establishes the complete-pipeline prefill regression on matched tokens. The candidate's faster CUDA arithmetic by itself does **not** translate into faster delivered prefill under this 2048-token schedule.

## Resources, recovery, and decision

Largest `metalAllocatedBytes` reported among the HumanEval requests was 34.89 GiB in both groups; this is a sampled worker counter, not a Mac-wide peak. Windows device peak VRAM, swap-out, 128K correctness, Q8 KV, and the full target gates in [`QWEN36-8BIT-TARGETS.md`](QWEN36-8BIT-TARGETS.md) were not measured in this experiment. The result cannot certify adoption. After the A/B, the original Mac LaunchAgent and Windows foreground agent were restored; a 17-input/16-output real `cuda-metal-split` request succeeded through the coordinator.

Keep [code PR #51](https://github.com/LittleLittleCloud/Infer.NET/pull/51) unmerged pending a different scheduling design. The next useful experiment is BF16 GEMM with smaller streaming windows or early 32-token delivery inside a larger compute tile, then repeat the matched fixed request and 20-task comparison. Do not change the default based on the native CUDA-compute number alone.

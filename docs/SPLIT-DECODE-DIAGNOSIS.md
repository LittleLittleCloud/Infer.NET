# Split Decode Cold Start Diagnosis and Deployment Plan

2026-10-22 (America/Los_Angeles). Related to #3, #4, PR #8. This record is for diagnosis and design; it has not passed formal performance acceptance, nor has a resident service been installed.

## Actual Measurements

Both instances were Qwen3.6-35B-A3B affine8/group64, with a fixed revision as per performance targets; FP32 KV/GEMV/recursive state, 19-token input, 256-token fixed output. Prompts were identical, and all output token IDs were identical. No prefix cache hit.

The first output is generated by prefill, so the numerator is 255. The previous startup script incorrectly used 256, displaying 9.16 t/s; corrected to approximately 9.12 t/s. This only explains the display error in 0.4%.

The new diagnosis uses dual-end Native AOT; 676 item values passed checks, 256/256 greedy tokens matched the reference, 5 handover protection passed, and both ends exited 0. The full Mac reference decoding for the same input is estimated at approximately 67.72 t/s based on logits file write time; this is a file-time estimate, not a formal timing metric.

Tested plugged in, High Power. The old 5bit worker was retained, and other applications were not closed. The entire machine's VM was sampled approximately every 2 seconds; the entire load/reference/dual-machine test took approximately 94.6 seconds, with new swap-in of 6.69 GiB and swap-out of 7.84 GiB. In the sampling window of approximately 8 seconds, surrounding the dual-machine decode, new swap-out was 0 and swap-in was approximately 11.84 MiB. The sampling window was approximately aligned via local file times; these whole-machine counts cannot be precisely attributed to the model or a specific token. The original slow run did not collect per-token and paging data.

This is not a fully controlled A/B test: reference prefill, file I/O, and system resident states differed, and there was only one round. Stable speedup of 6.36 times cannot be claimed, nor can the memory threshold be declared passed based on this.

## Bottleneck Judgment

1. **Decode per-token network communication has been excluded.** After `SplitInference` receives all states and End, the generation loop only calls local `MetalSplitSession.Forward`. The approximately 0.6 seconds for handover are counted in prefill, not in the 27.95 seconds here.
2. **The primary suspect is first-time GPU usage and memory residency.** Ordinary split only runs 20 layers of prefill on the Mac; although the first 20 layers are loaded, the first full decode is only used on the Mac. The verification mode ran all 40 layers first and repeated the same output. The improvement from 9.12 to 58.07 t/s supports this direction, but it cannot yet be determined if the original slow time was concentrated in the first step.
3. **FP32 diagnostic configuration has a cost but cannot explain the entire gap.** The launcher cleared DEEPINFER configuration, disabled matrix prefill, used 32-token chunking, sequential Delta, and FP32 KV, without enabling BF16 fused attention. GEMM/Delta chunking switches mainly affect prefill; decode still uses the original fused expert GEMV, GPU argmax, and one command buffer per token. The short context from 19→274 is insufficient to assume a multiple-fold gap solely based on KV width.
4. **Lack of resident service.** Currently, both ends restart for each request, load weights, and use the GPU for the first time. Although model loading is excluded from result timing, the latency from residency/first execution can still enter decode. `--verify` is a diagnostic tool and cannot serve as a formal warm-up solution.

The next localization step should record wall/GPU time for each step, submission wait times, and VM increments for loading/warm-up/formal request phases. Using the same process, same precision, and same input, measure the first request first, then warm up and measure three times; then perform a single Mac/dual-machine control under the same conditions. BF16 recovery requires passing another numerical threshold; do not use precision changes to mask issues.

## Formal Deployment Design (To be implemented)

- Mac: Lightweight coordinator/API + standalone Metal worker. Only the worker loads a complete 8bit model, balancing prefill for the first 20 layers and all decode steps. TUI, CLI, and Web all connect to the same API, eliminating the need to start separate models.
- Windows: Persistent CUDA worker, loading weights for the first 20 layers once and waiting for requests. Maintain the existing home network; SSH is used only for installation, upgrades, and diagnostics, and normal inference does not depend on an SSH session.
- Initial request concurrency 1, with a bounded queue; the state machine is Loading → Warming → Ready → Busy → Ready. Warm up the complete 40 layers and decode, clearing KV/Delta/convolution buffers before accepting traffic. Model allocation does not equal Ready.
- Short inputs can explicitly route via Mac-only based on measured crosspoints, with routing recorded; long inputs use both machines. It cannot be assumed that short inputs are faster on dual machines. The current CUDA serial token prefix still requires batched operator optimization.
- Requests support streaming output, natural EOS, cancellation, timeout, length validation, and explicit finish reason; benchmark mode retains fixed output separately. The current 2K/256 limitation must be displayed in the capability interface; 128K is not enabled until acceptance.
- Mac uses a launchd user LaunchAgent, remaining resident after login; if unattended startup is required, verify the Metal environment under LaunchDaemon separately. Windows integrates Windows Service lifecycle, running under a dedicated low-privilege account; installing the service is a separate administrator installation step.
- Release two versioned Native AOT packages: osx-arm64 (executable, Metal dylib, service template), win-x64 (executable, SM89 CUDA DLL, required runtime dependencies, service installation script). Check OS/GPU/driver compatibility before deployment; target machines do not need source code, compilers, or SSH to run requests.
- GitHub Releases publishes binaries, checksums, and manifests; the manifest fixes source SHA, backend ABI, protocol, model revision, quantization, and state layout. Models are managed and hashed separately, not bundled into the application package. Configuration/keys/logs are separated from the version directory.
- Control API and cross-machine state transmission use TLS, with worker mutual authentication; existing request/location/integrity checks are retained. The current HMAC channel is unencrypted; TLS is a pending implementation item.
- Upgrades first drain the queue, stop the old worker, verify the new version and warm up, then enable traffic upon passing; failover reverts to the old version. 48 GiB Mac does not load both old and new complete models in parallel, so the initial version accepts a maintenance window. The coordinator does not replay requests for tokens already output; failed requests discard state and report explicitly.
- Operational metrics include startup/warmup time, queue duration, client first token, handoff time, decode segment speed, GPU usage, total machine swap increment, failure reasons, and version. Single-machine regression, BF16 values, and 128K fixed targets are still accepted according to `QWEN36-8BIT-TARGETS.md`.

System service references: [Apple launchd](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html), [Microsoft Windows Service](https://learn.microsoft.com/en-us/dotnet/core/extensions/windows-service).

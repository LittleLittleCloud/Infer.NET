# CUDA affine8 GEMM and expert candidate, 2026-10-23

Issue [#38](https://github.com/LittleLittleCloud/Infer.NET/issues/38) tracks this opt-in SM89 experiment. The deployed `919259d` Mac serve and Windows agent were left unchanged. All numbers below are **single-operator CUDA-event measurements**, not full-prefix, cross-host or 128K throughput. A resident but idle Windows agent occupied about 21 GiB of the 4090's 24 GiB; the microbenchmarks used a separate source checkout and small allocations. The operator scripts warmed up once and reported three trials of five launches each. Their raw results remain local on Windows under the indicated `artifacts/dual-host` directories; they are not public downloads.

## Dense BF16 GEMM: vectorized affine8 tile loading

The existing 32 × 64 output tile used the same BF16 Tensor Core MMA before and after this change. The candidate loads eight adjacent affine8 weights together and loads their shared group64 scale and bias once, then converts each dequantized value to BF16. It preserves BF16 input operands and FP32 accumulation. The candidate at `4c0aed36064914f0229414363d49d00c59052012` was compared with unchanged `main` at `e017d84e805c016d5912b5051e4c69f758056363` on the same RTX 4090, using `scripts/windows/benchmark-prefill-ops.ps1`. The independent double-BF16 oracle covered small/tail shapes; all large shapes had relative L2 below `7.3e-7` and max absolute error below `4.8e-7` against the SIMT BF16 operator. Both runs reported `passed=true`.

| Tokens × rows × cols | Old Tensor Core median | New Tensor Core median | Kernel-only speedup |
|---|---:|---:|---:|
| 32 × 8192 × 2048 | 0.2133 ms | 0.0692 ms | 3.08× |
| 128 × 8192 × 2048 | 0.2517 ms | 0.1071 ms | 2.35× |
| 512 × 8192 × 2048 | 0.7641 ms | 0.3463 ms | 2.21× |

The raw baseline/candidate directories are `gemm-experts-e017d84-ops` and `gemm-experts-4c0aed3-ops` under each checkout's ignored `artifacts/dual-host` directory. These figures do not establish a deployed speedup: `batch-fp32` does not use the BF16 Tensor Core kernel, and the BF16 model path has outstanding cross-backend quality checks documented in [the stage probe](BF16-STAGE-PROBE-20261023.md).

A same-binary check at `25b0153` retained the original scalar tile loader alongside the candidate: all six shapes, including non-full rows/tokens, produced **bitwise-identical Tensor Core output**. The 32 × 8192 × 2048 scalar/packed medians were 0.2134/0.0690 ms. The checker reported `passed=true`; its raw JSONL SHA-256 is `b6bb0536ff827d74ef0c24a4c70f751e947aff4dcb8f0c7aa38089a8ba4da2c5` in `gemm-experts-25b0153-ops`. The GPU was in P8 at 31°C and 7.34 W before warmup, with 21107 MiB allocated by the resident agent; CUDA events cover warmed kernel execution, not model loading or transport.

## FP32 expert and dense candidate

The new `batch-fp32-fast` option combines three FP32 changes while retaining the existing 32-token chunk and FP32 KV:

- Dense projections reuse packed affine8 weights over a 4- or 8-token tile. The earlier operator checker verifies bitwise equality with the original GEMV across tail, large QKV and output-projection shapes; the 32 × 8192 × 2048 case measured about 0.43 ms versus 0.64 ms for original GEMV in the latest isolated checker.
- Routed experts use the existing aligned packed-weight kernel. At `e3dce22`, the 32 × 4096 × 2048 gate/up-shaped case measured median **2.38 → 1.73 ms** and the 32 × 2048 × 4096 down-shaped case **2.37 → 1.69 ms**. Routed and non-routed outputs matched original FP32 GEMV bitwise. This is an activation of an existing validated primitive in the new mode, not a new Tensor Core expert GEMM.
- The shared expert's gate/up projections share one kernel launch and activation load stream. At `2a98284`, 32 tokens × 512 rows × 2048 columns with one shared expert measured median **0.0836 → 0.0327 ms**, with outputs bitwise equal to the two production SIMT kernels.

The first attempt to fuse the **large routed** gate/up matrices was a negative result: for 32 tokens × 8 routes × 4096 rows × 2048 columns, separate packed kernels took about **3.48 ms**, while dual-accumulator fusion took **4.83 ms**. A single-launch dispatch variant also took about **4.82 ms**. Both were bitwise correct. The final candidate keeps large routed gate/up separate and fuses only the small shared expert. The failed measurements remain in `gemm-experts-de4e1bc-reuse`, `gemm-experts-9760a33-reuse`, and `gemm-experts-25863e2-reuse` on Windows.

The routed expert checker at `e3dce22` passed with JSONL SHA-256 `94acc1d99a50b3dd6e69cc7c5ac624d055147ccf1bcd72ebf028cbe012ad07a8`. The shared-expert checker at `2a98284` passed with JSONL SHA-256 `bef9dfa6dc3a95fa9d25c8fbb326ed115a31d7559bef15658e148a7496efdb85`. At `cbff46a`, the native SM89 DLL and managed Host built on Windows, Windows tests passed 127 with one Metal-only skip, and Mac tests passed 128; the Host build also passed on Mac. These establish build and operator correctness for the candidate, not full-model equivalence.

## Isolated full-prefix A/B and restoration

With the user's permission, the verified old Windows agent was briefly stopped to load the pinned 8bit prefix into a separate candidate process. The old `919259d` executable and config were restored after each run. The final restoration is a foreground SSH session, PID `6276` at the time of measurement; the 4090 again held about 20011 MiB, Mac `/ready` returned HTTP 200, the coordinator reported a healthy connected agent, and a real 16-token request returned HTTP 200. The first attempted detached `Start-Process` restoration did **not** survive SSH logout; it was immediately replaced by foreground execution. The automation now explicitly uses the foreground mode. These are recovery facts for this run, not a claim of Windows Service installation.

The candidate DLL SHA-256 was `ce04673d942c0a4eef298ad1a38ea1cae41ad5d8e00ba4e54e3378896ca81bbe`; its native/managed source did not change between `25b0153` and the script-only runs below. The benchmark loaded the same pinned prefix once per run, used FP32 KV and 32-token native chunks, verified 131 synthetic token IDs including irregular tails, then alternated one warmup and three measured 512-token passes per mode. All 20 layer traces, final hidden vectors, all 40 KV/Delta state tensors, incremental KV versus final KV, and the 512-token hidden hashes were bitwise equal. The comparison does **not** include Mac suffix, logits, network, decode, real prompt tokenization or 128K behavior.

| Same-binary FP32 comparison | Baseline median | Candidate mode 6 median | Native prefix-only change |
|---|---:|---:|---:|
| Mode 1 → mode 6, source `8c0e76c` | 0.7679 s, 667 tok/s | 0.5432 s, 943 tok/s | 1.41× versus older unpacked mode |
| **Deployed packed mode 5 → mode 6**, source `4e00cae` | **0.5493 s, 932 tok/s** | **0.5408 s, 947 tok/s** | **1.016×, 1.55% less time** |

The current deployed agent advertises `batch-fp32-packed`, which maps to mode 5. Therefore the second row is the relevant incremental comparison. Mode 5 already uses packed dense and routed expert kernels; mode 6's remaining change is principally the small shared-expert fusion. The large operator-only speedups cannot be projected onto the present service. Each run's raw `result.json`, 40 state files, traces and log are local-only under Windows `artifacts/dual-host/gemm-experts-full-ab-8c0e76c` and `gemm-experts-packed-ab-4e00cae`. Their result JSON SHA-256 values are `80f47afff7516ee092acb6031a13a027cfbd3b6c8bda26b76032a2021dca4c2a` and `cfe8492ad3a3dced50af4ebaf7bcbca678788dcbcfed3887b55ae611798d2b7e`, respectively. The 512-token timing is a diagnostic, not a target acceptance run.

`batch-fp32-fast` remains opt-in. The real split RPC and complete-generation checks below have since run; suffix logit equivalence, memory and 128K cold-prefill/long-decode gates in [the fixed target](QWEN36-8BIT-TARGETS.md) remain open. The modest mode 5 → 6 gain means the next performance work should focus on larger routed expert computation and overall chunk execution, with correctness checked at each arithmetic change.

## Current-branch worker evaluation

The Windows agent was built from `perf/cuda-gemm-experts` source `c37f939dffae9eae2a1c323ebb1d1468abdcd645`, packaged and verified as an immutable win-x64 release, and started with `cuda-prefill=batch-fp32-fast`. The unchanged Mac coordinator and `split-serve` ran source `e017d84e805c016d5912b5051e4c69f758056363`. Both used the pinned Qwen3.6-35B-A3B affine8 weights, FP32 KV, split protocol v4 and the same model revision. The Mac short-prefill route was temporarily set to zero so every evaluation request used the Windows agent. A real 18-token smoke request reported `cuda-metal-split`. Windows CUDA self-tests passed; .NET tests passed 127 with one Metal-only skip. This is a mixed-source evaluation of the **current-branch Windows worker**, not a deployment of that branch's Mac binaries.

Pi 1.4.0 ran the fixed 20-task HumanEval cohort, seed 0, with a 300-second per-task timeout, 32,768-token advertised context and 4,096-token output cap. The pinned compressed dataset SHA-256 was `b796127e635a67f93fb35c04f4cb03cf06f38c8072ee7cee8833d7bee06979ef`. All **20/20** tasks completed, created syntactically valid `solution.py`, and passed the official HumanEval assertions in isolated offline containers. Total Pi wall time was **714.77 s** (median task 27.81 s, p90 55.86 s), across 101 model requests and 250,989 reported tokens. These are application and correctness results, not 128K performance acceptance. The same cohort on the older `e017d84` deployment had previously taken 808.88 s with 20/20 valid solutions, and a second run took 774.29 s with 19/20 Pi completions because of one malformed tool call. Request counts, token counts and network conditions differed, so those totals do not isolate a kernel speedup.

For a closer A/B, the same Mac serve process, prompt text, FP32 KV and one-token output were held fixed while only the Windows agent switched between `batch-fp32-packed` (`e017d84`) and `batch-fp32-fast` (`c37f939`). Three requests per input size were measured; the values below are medians. `cudaCompute` is the relevant Windows computation measure; `prefill` also contains the overlapping Mac suffix and cross-host handoff. The `send/write` stage overlaps computation and is not a pure network latency.

| Input | Old CUDA compute | Current-branch CUDA compute | Old full prefill | Current-branch full prefill |
|---|---:|---:|---:|---:|
| 2,325 tokens | 2.605 s | **2.576 s** (1.12% less) | **4.154 s** | 4.270 s (2.78% more) |
| 18,453 tokens | 24.874 s | **24.607 s** (1.07% less) | 31.317 s | **27.178 s** (13.22% less) |

At 18,453 tokens, the old/current-branch `send/write` medians were 30.206/20.969 s over Wi-Fi. That variance dominates the full-prefill difference and cannot be credited to GEMM. The roughly 1% compute improvement agrees with the isolated mode 5 → 6 result above. This experiment does **not** support promoting the fast mode as a major prefill breakthrough. Raw Pi records, Docker assertions, per-request metrics and exact runtime provenance remain in the local ignored `artifacts/humaneval-cuda-gemm-c37f939-20261023/` directory.

Immediately after measurement the candidate agent was stopped. The old Windows agent and the original Mac LaunchAgent were restored; a short request again reported `metal-local`, and a longer request reported `cuda-metal-split` through the restored agent. The user then requested that the candidate remain running. The verified old Windows process was stopped again, the immutable `c37f939` agent was restarted in a retained foreground SSH session, and the Mac LaunchAgent was restarted with `short-prefill-tokens=0`. A new 18-token request through the coordinator reported `cuda-metal-split`, and the Windows log confirmed `batch-fp32-fast` from `c37f939`. The Windows agent is **foreground SSH hosted, not an installed Windows Service**; loss of that session can stop it. The prior Mac configuration was saved privately for rollback. The candidate remains opt-in in source. Matched suffix-logit checks, longer contexts, memory residency and the 128K target are still unverified.

## Controlled HumanEval prefill/decode A/B, 2026-10-23

The later speed comparison held the **same Mac split-serve process** (`6a0d55d6237d1c5322f282696b5d1a33d127f79d`, PID 30590) and coordinator throughout both 20-task runs. That Mac build adds one completed-request `INFERENCE_METRIC` line; it makes no CUDA kernel change. Only the Windows agent changed: `main` inference source `e017d84e805c016d5912b5051e4c69f758056363`, `batch-fp32-packed`, versus this branch's `eb492b9dd443ce3335fb86c87df80ddf2b6b6a7e`, `batch-fp32-fast`. Current `main` commits after `e017d84` add documentation and the test harness, not inference code. Both immutable Windows packages verified. The agent configs differ only in `cuda-prefill`; pinned affine8 weights, model revision `e06a74e6236a60c8367e1a3214e83d8b61b637b0`, FP32 KV, Mac suffix configuration, TLS data channel, Wi-Fi route, AC power, and the Pi 1.4.0 harness were held fixed. A short real request verified `cuda-metal-split` and the new per-request log before measurement.

The pinned 20 HumanEval task IDs and seed 0, 300-second per-task timeout, 32,768-token advertised context and 4,096-token output cap were identical. Each task ran once per agent; failures were retained. The `main` run had 19/20 Pi completions, with HumanEval/161 marked incomplete; the branch had 19/20, with HumanEval/50 marked incomplete. No timeout occurred. Official assertions were **not** run in this speed A/B. The worker metric log covered **99/99** `main` and **103/103** branch model requests; every request reported `cuda-metal-split`. Speeds below are `sum(input tokens) / sum(prefill seconds)` and `sum(decode token intervals) / sum(decode seconds)`, not Pi wall-time throughput.

| Fixed 20-task HumanEval workload | `main` packed | Branch fast | Branch change |
|---|---:|---:|---:|
| Worker prefill | 561.62 tok/s | 532.33 tok/s | **−5.22%** |
| Worker decode | 66.15 tok/s | 64.28 tok/s | **−2.83%** |
| Pi application wall time | 753.85 s | 759.34 s | +0.73% time |
| Model requests | 99 | 103 | +4 |
| Input / output tokens | 235,872 / 21,576 | 237,271 / 19,624 | Different request mix |

The aggregate rates answer what these two real Pi runs experienced, but their different prompt lengths, request counts and output paths do **not** isolate the CUDA change. To control input and decode length, the same Mac process then ran fixed 2,325- and 18,453-token prompts with 256 forced output tokens. Each mode/input had one excluded warmup and three measured requests. The first A/B medians were:

| Fixed input / 256 output | `main` packed | Branch fast | Branch time change |
|---|---:|---:|---:|
| 2,325: CUDA compute | 2.936 s | 2.777 s | −5.43% |
| 2,325: complete prefill | 4.256 s | 4.343 s | **+2.04%** |
| 2,325: decode | 64.95 tok/s | 64.57 tok/s | −0.59% speed |
| 18,453: CUDA compute | 25.108 s | 24.871 s | **−0.94%** |
| 18,453: complete prefill | 27.477 s | 27.508 s | **+0.11%** |
| 18,453: decode | 52.10 tok/s | 51.09 tok/s | −1.95% speed |

A later long-input A–B repeat, again three measured requests per mode, found `main`/branch medians of **28.388/27.993 s** for complete prefill and **25.123/24.755 s** for CUDA compute. Pooling the six measured long-input requests per mode gives prefill medians **27.578/27.559 s** (−0.07% time) and CUDA-compute medians **25.116/24.838 s** (−1.11% time). The ~0.9 s drift in `main` prefill between its two visits is far larger than the ~0.02–0.03 s pooled/first-pair difference. Mac decode code was identical in both modes; its small observed difference cannot be attributed to the CUDA prefix kernel. CUDA `send/write` also overlaps computation and is not a standalone network latency.

**Decision:** the retained fast path has a reproducible, roughly **1% long-prefix CUDA-compute benefit** over the deployed packed path, but **no demonstrated end-to-end prefill or decode speed benefit** on this Wi-Fi 8bit/FP32-KV deployment. The branch should not be promoted on a claim of user-visible performance gain. The HumanEval application run was slightly slower and its raw worker rates were lower; the fixed-input test narrows the causal conclusion to “compute improves slightly, complete prefill is effectively unchanged.” This is not a Q8-KV or 128K target acceptance result. Raw run manifests, every Pi task, metric summaries, fixed-request results and filtered per-request service log lines are local-only under `artifacts/dual-host/humaneval-ab-6a0d55d-20261023/`; the `main`/branch `worker-metrics.log` SHA-256 values are `dfb9f8230b839bde9d5407a2fd0d5242e977cc193940a9c9f366991c22f5e4bd` / `cbeb3afbdaf8a1e9eaa844015ca9bfbdb40106d2266aa1a1020387a26b18f02b`. The two HumanEval `performance.json` files record the actual Mac/Windows commits and one-line change description. After the A/B, the branch agent was restored as the active foreground process with the same Mac serve.

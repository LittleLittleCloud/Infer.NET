# CUDA QK score reuse: operator gain, no dual-host gain

Historical experiment only: the opt-in CUDA implementation remains on its archived branch and is not part of the integrated serving code. The measurements below are retained as evidence.

2026-10-23 · [Issue #3](https://github.com/LittleLittleCloud/Infer.NET/issues/3) · candidate binary source `1905767cf466f26415708da3b8a9b6469c72e78d` on `codex/cuda-query-reuse`.

The retained attention score kernel reads the same keys independently for each query in a 32-token chunk. The opt-in `--cuda-prefill batch-fp32-score-reuse` kernel shares those key loads between two queries while preserving each query's FP32 accumulation and reduction order. The default remains `batch-fp32`; the A/B control here was the existing opt-in packed mode `batch-fp32-packed` (native execution mode 5), versus packed plus score reuse (mode 6). This experiment changed neither the affine8/group64 weights nor the deployed FP32 KV format.

## Correctness and operator diagnostic

On the RTX 4090 SM89, a standalone checker compared every valid score element and final attention output bitwise for 40 cases: 17, 257, 4096, 32768 keys with irregular query tails, plus 131072 keys / 32 queries, each with FP32 and BF16 KV. At 131072 keys / 32 queries, hot-data full attention changed from 84.363 to 47.686 ms with FP32 KV and 23.609 to 17.860 ms with BF16 KV. QK scoring alone changed from 73.316 to 37.072 ms FP32, and 14.983 to 9.197 ms BF16. These are CUDA operator measurements, **not** model prefill or dual-host throughput. Local Windows raw JSONL SHA-256: `2916460caebc2e9c25b84b930313b022c648d72b651e4a17ae75b3f5004eab10`.

The pinned 8bit prefix bundle was then run in both modes. At 131 synthetic tokens with irregular 1/7/17/32 chunks, all hidden chunks, all 20-layer traces and all 40 final state tensors matched bitwise. At 32768 fixed token IDs, all hidden chunks and final states matched bitwise. One cold-order front-20-only run measured 49.976 s for mode 5 and 46.541 s for mode 6; state export was excluded. This one-run diagnostic is not a formal speed comparison. The 32768-token input JSON SHA-256 was `4248176bd03278693b6573f6bb63990d65f773259d8dde63256cbcd6b22ba50b`. Local result JSON SHA-256: 131-token `7f5ea8533369e1806c7905982770b374cf4690a8cb908d8e6bf0f82f13b59273`, 32768-token `9175738750db6829454c168dcceca266e02b3a139e1b54216fca79000a2741fd`.

## Same-package dual-host A/B

Mac M5 Pro 48 GiB ran coordinator and full-model serve; Windows RTX 4090 ran the prefix agent. Both Native AOT packages came from the exact source commit above. The candidate Mac serve stayed in one process while only the Windows agent switched between modes. Mac package executable SHA-256 `38de094b85cbe971e863d478d54c85d74ff4468797889efb009518bd5b170fbf`, Metal library `1739ff5dd22a4b158f97d84d39268478a75d5683f4a9ad1a3cd0d1a8f79d4aef`; Windows executable `ea91098c9d4d87720aacf86de454bb0b87b6ea4fe28e5c4c4b0a4943366a1c9f`, CUDA DLL `096be9bc235ce992eca06be581aeb9750bf982ad51c24e7c119881e944218f83`.

The model was affine 8bit/group64 with FP32 KV and FP32 prefill GEMV. Each fixed prompt produced exactly 8192 or 32768 actual input tokens; each request generated 16 fixed output tokens, ignored EOS, reset model state and had 0% prefix hit. Mac was on AC power. For each mode and length we excluded one complete warmup and kept all three measured requests. The route was `cuda-metal-split`; final output token IDs matched across modes at each length. This is a **diagnostic FP32 KV workload**, not the BF16/131072+4096 acceptance workload.

The 32768-token wire payload was 972,455,936 bytes in both modes. The CUDA `send` accumulator overlaps compute and includes producer backpressure; it is **not** a pure network-transfer clock and cannot be added to CUDA compute. The Mac suffix remained about 51.25 s, while CUDA total elapsed stayed around 52.7–52.9 s despite the shorter CUDA compute component. This is consistent with the pipeline and send/receive waits hiding the QK improvement; the A/B does not isolate an individual transfer cause. Metal allocation peaked at 36.076 GiB for 32768 and 34.894 GiB for 8192, below the fixed 38.5 GiB budget. Measured rounds recorded zero whole-system additional swap-out; the control's 32768 warmup recorded 54.094 MiB and is retained separately. We did not sample whole RTX 4090 peak or prove the 128K memory budget in this diagnostic.

The candidate was **not selected as the default**. The original `919259d290855b1ce0401374bf8b3d781ed1ed43` Mac LaunchAgents and Windows foreground agent were restored. The coordinator and serve became Ready with the agent connected, and a real 8192-input/16-output split request returned the same token IDs as the candidate. The candidate code remains opt-in for subsequent attention experiments. It does not satisfy the fixed 128K BF16 prefill/decode/resource gates in [the target specification](QWEN36-8BIT-TARGETS.md).

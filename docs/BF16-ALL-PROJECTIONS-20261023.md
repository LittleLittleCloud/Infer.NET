# CUDA high/low BF16 projections and KV precision, 2026-10-23

This is an isolated correctness diagnostic for the 20-layer CUDA prefix of Qwen3.6-35B-A3B, not a serving benchmark or a deployment. The fixed acceptance criteria remain in [QWEN36-8BIT-TARGETS.md](QWEN36-8BIT-TARGETS.md). Candidate source is `a20449e1e818af5760076a83f822f5bceec07967`; the Windows SM89 DLL SHA-256 is `5d383567f4e63dc39b61fb040e1aca369c6156224dd8b6b0e028ed99474c4b54`. The model uses the pinned affine8/group64 weights and 128 fixed synthetic token IDs. The independent reference is serial MLX FP32 arithmetic on the same quantized weights. MLX is used only as an offline oracle; product inference remains CUDA/Metal. The retained Metal FP32 control was captured at source `1f42e6f` and is a separate device check, not a same-full-commit formal two-host acceptance run.

The opt-in `DEEPINFER_CUDA_ALL_HIGHLOW=1` / `-HighLowAll` path uses three BF16 Tensor Core products for each projection: `W_hi·X_hi + W_hi·X_lo + W_lo·X_hi`, accumulated in FP32. It includes QKV, output and expert projections. It does not change the default/deployed worker. Router and shared projections were kept FP32 in both diagnostic runs.

With FP32 KV, the full 20-layer candidate passes the specified per-layer relative L2 and max-absolute thresholds against the independent oracle; its worst Metal FP32 layer/state relative L2 is `2.6061e-5`, and there is one *ordered* expert-route difference but no expert-set difference in 2,560 decisions. This is substantial numerical progress for the projection arithmetic, but it does **not** satisfy the target profile because the target requires BF16 KV.

With BF16 KV, both the candidate and its internal FP32-GEMM control first fail at layer 3, the first full-attention layer (`full_attention_interval=4`). Their layer-3 relative L2 values against the independent oracle are `4.0836e-4` and `4.0859e-4`, respectively. The close match at the first failure supports KV storage/read precision as the immediate remaining source, rather than high/low projection arithmetic. Later error and route differences compound, so this evidence does not assign every later mismatch solely to KV. There is no independent oracle KV/state trace in this run, and no real RPC transfer, Mac suffix, logits, greedy output, 128K input, memory gate or serving-throughput result. Instrumented probe seconds contain readbacks and are not throughput evidence.

## Matched CUDA K/V export check and interrupted oracle

The same-source/same-DLL FP32-KV and BF16-KV candidate exports were compared byte by byte with round-to-nearest-even BF16 conversion. At layer 3, **all 65,536 key and 65,536 value words** in the BF16 run exactly equal the rounded FP32-KV export. Expanding those BF16 words to FP32 yields relative L2 `0.0016626` for keys and `0.0016550` for values versus the original FP32 exports. At later attention layers, the number of BF16 words differing from rounded FP32-KV runs rises, consistent with propagated activation differences; those later comparisons do not isolate storage rounding. The reproducible checker is `scripts/split/analyze-bf16-kv-rounding.py`; its local result JSON SHA-256 is `8307d2df4e076c10aad05a3ee568c232da469dfaab4947194e116eda40b572e8`. This establishes the layer-3 CUDA storage conversion and excludes a simple byte-layout mismatch there, but does not prove the attention kernel or independent state reference passes.

An optional MLX oracle mode now stores K/V as BF16 and expands them for FP32 attention, solely to isolate the expected storage loss. Its small cache smoke test passed. A full 35 GiB model run at source `0f41310` was **stopped before the first reference token** when Mac system-wide swap-out rose by at least 9.375 GiB in approximately 34 seconds of observation. The counter covers the whole host, so it cannot all be assigned to the oracle process. The old Mac serve was then restored, reattached to the original Windows agent and verified Ready/connected. This aborted attempt produced no oracle layers or logits; it is neither a pass nor a numerical failure. The local abort record SHA-256 is `db45a7355dae4ac29425cd050784e4a7f12fd70a33e4c3b3478b254b7336ebc9`. Future independent BF16-KV work needs a memory-bounded prefix-only oracle or a separate free-memory window; do not repeat the full-model load under the same pressure.

# HTTP chat APIs and TUI playground

Implementation branch `codex/tui-dashboard`, associated with Issue #13, superimposed on chat PR #12. The model remains Qwen3.6-35B-A3B 8bit / FP32 KV. The candidate version removes the original deployment's artificial limits of 2048 context / 256 output; input plus output is constrained by the fixed model native window of 262144 tokens, actual memory, and request deadline. This capacity claim does not represent that 262K full-model or performance acceptance has passed.

## Entry Points

Unified access to the Mac coordinator, currently deployed as `http://127.0.0.1:5200`. The TUI default port has changed from 5100 to 5200. Worker local HTTP 5201, Windows actively connects to Mac data port 5210; computing responsibilities remain unchanged.

| HTTP Path | Request Body | Non-streaming | `stream: true` |
|---|---|---|---|
| `/v1/chat/completions` | `model`, `messages`, `max_tokens` or `max_completion_tokens`; optional function `tools` | `chat.completion` | `chat.completion.chunk`, optional usage, `[DONE]` |
| `/v1/messages` | `model`, `messages`, required `max_tokens`, optional top-level `system` | Claude `message` | message_start → content_block_start/delta/stop → message_delta → message_stop |
| `/v1/responses` | `model`, `input`, optional `instructions`, `max_output_tokens` | `response` | created/in_progress → output_item/content_part/text events → completed or incomplete |
| `/v1/models` | GET | Currently healthy models supporting structured chat | N/A |

The compatible interface is the text chat API format; inference is executed by the local Qwen, without calling OpenAI or Anthropic cloud services. Using existing cluster tokens: supports `Authorization: Bearer TOKEN`, `x-api-key: TOKEN`, or `X-DeepInfer-Token: TOKEN`; internal registration/RPC still requires the original headers. By default, HTTP only listens on loopback, and cross-host data channels maintain mutual TLS.

Supports system/user/assistant text messages and text content blocks; Chat/Responses' developer role maps to system. Messages API uses top-level system. Responses input can be a string or complete message history, and can also return assistant message items generated by this implementation. Currently, the last message must be from the user; assistant pre-filling is not supported. All history is encoded by the worker into Qwen message templates according to roles; literal special tokens in the user's body do not act as role separators.

Only `*-chat-v1` workers can process structured history; older workers are excluded to prevent older versions from ignoring new fields. Old `/v1/infer` and `/v1/infer/stream` remain available.

## Explicit Capability Boundaries

- Current greedy decoding: omits temperature/top_p, or passes `temperature: 0`, `top_p: 1`; Chat's `n` can only be 1.
- Chat Completions supports function `tools`, `tool_choice` (`auto`, `required`, `none`) and tool result history. The service converts Qwen's call text into structured `tool_calls` for the client to execute tools; Infer.NET itself does not execute shell or file operations. Streaming responses for tool requests wait for the model to finish generating before emitting the call event. `required` is currently only a hint and does not guarantee the model will choose the tool.
- Tool calling for Messages and Responses is not yet implemented. Image/audio, JSON schema/JSON mode, custom stop tokens, logprobs, and non-greedy sampling are also not implemented; related parameters return 400 and are not silently ignored.
- Responses is a stateless interface and does not store responses; `store: false` can be passed. `store: true`, previous_response_id, background responses, and conversation storage are not supported. Multi-turn requests explicitly retransmit history, re-prefilling each turn, with no prefix cache.
- When Chat/Responses omit the output limit, the remaining model window is used, stopping upon EOS; Messages still requires explicit max_tokens. TUI defaults to Auto, similarly not reserving the entire window's KV, but expanding on demand during decoding while retaining existing state.
- Exceeding limits returns an error, without automatically truncating history. Upon reaching the output limit, Chat returns length, Messages returns max_tokens, Responses returns incomplete/max_output_tokens; EOS returns stop, end_turn, completed respectively.
- Streaming text is true incremental. input/output usage comes from worker token counts, not character count estimation. Downstream 429/ input errors retain HTTP status before streaming starts; errors after streaming starts are reported via events, without sending a successful completion marker, and without retrying partial outputs.
- Other provider paths are not implemented, such as file uploads, Response retrieve/delete, or Messages token-count API. SDK interoperability only represents the above text subset.

## TUI

Run in the repository root directory:

```sh
dotnet run --project src/DeepInfer.Tui -c Release
```

When no address parameter is provided, if a local `artifacts/deploy/private/mac/coordinator.json` deployment exists, the TUI reads its listen/token-file to connect to the current deployment. You can also explicitly specify the address, passing credentials via environment variables:

```sh
export DEEPINFER_TOKEN_FILE=/PRIVATE/mac/token.txt
dotnet run --project src/DeepInfer.Tui -c Release -- http://127.0.0.1:5200
```

The TUI calls the public Chat Completions interface via `InferChatClient : Microsoft.Extensions.AI.IChatClient` in the Runtime, providing GetResponseAsync and GetStreamingResponseAsync. The UI uses streaming per turn; system prompt, history, model, and output limit are passed from a unified adapter, bypassing the coordinator.

The interface uses a three-part header/body/footer layout with no borders. The header fixes the title, tabs, and connection status; the body occupies the remaining height; the footer fixes the input area, actions, request statistics, and connection address. The default is Dashboard, with another tab being Playground. When the width is at least 100 columns, the Dashboard left side shows the worker list and the right side shows status details; in narrow windows, they are arranged vertically. Terminal resizing does not lose drafts or conversations. Mouse clicks are supported for tabs, workers, buttons, and input fields, and the scroll wheel can be used to browse workers or conversations. The Dashboard displays heartbeat, online/offline status, serve status, attached agent connections, queue count, completion count, quantization and window size, prefill/decode times for the most recently completed requests, and Metal/KV allocation; data not reported is explicitly shown as unknown, without fabricating GPU utilization. Windows agents are attached devices of serve and do not impersonate independently registered workers. Switching tabs preserves conversations, drafts, and ongoing generations. The Playground includes a chat area, input box, action row, and statistics. Enter sends, Tab moves focus, and Send/Stop/New chat/Settings/Older/Latest are available; Settings adjust the system prompt and output limit; the default is `auto`, but positive integers can also be entered. Mouse reliance requires terminal support for SGR events, while Tab/Enter can continue to be used. During generation, the next round's draft can be entered, but a second request will not be submitted simultaneously. Stop retains partial output for viewing; cancelled or failed rounds are not added to the next round's model history; New chat clears the session. If history exceeds capacity, an explicit error is reported, and a new session can be actively started.

The bottom information bar displays the current coordinator's full Chat Completions and Responses URLs and the Claude Code base URL, and indicates the `/v1/messages` path. The Claude Code base corresponds to `ANTHROPIC_BASE_URL`; do not fill `/v1/messages` as base; authentication uses the original cluster token, and credentials are not displayed in the interface. Pi can call local tools via Chat Completions; Claude Messages tool calling and token-count API are not yet implemented, so full Claude Code compatibility cannot yet be claimed. Addresses are generated from actual connection configurations; the default loopback address only applies to local clients.

Dashboard prefill is displayed in seconds and explicitly includes pipeline state handover; it is not pure GPU prefill kernel time. Statistics are for recently **completed** requests; during the execution of current requests, old values are not falsely used as current latency. Playground displays first text time, output token count, and total request time, and does not falsely present average speed including network/prefill as model decode throughput. The TUI does not load models, does not start background workers, and does not have built-in tool execution permissions.

## Reproduction Testing

```sh
dotnet test tests/DeepInfer.Tests -c Release
python3 scripts/chat-integration.py
python3 scripts/chat-integration.py --executable /RELEASE/deepinfer
```

Protocol testing uses independent ports and controlled text workers, without occupying GPUs or modifying existing deployments. After additionally installing openai, anthropic, pexpect, and pyte into an independent test virtual environment, you can run `scripts/chat-integration.py --sdk --tui` to perform official SDK and real PTY interaction checks; these packages are not product dependencies. Real dual-machine model testing and deployment results are recorded separately; simulation checks cannot replace them.

The TUI refers to the conversation and input layout ideas of [RazorConsole LLMAgentTUI](https://github.com/RazorConsole/RazorConsole/tree/main/examples/LLMAgentTUI), retaining the fixed RazorConsole 0.6.0, without introducing its tool execution framework. Protocol basis: [OpenAI Chat streaming](https://developers.openai.com/api/reference/resources/chat/subresources/completions/streaming-events), [Responses events](https://developers.openai.com/api/reference/resources/responses/streaming-events), [Claude streaming](https://platform.claude.com/docs/en/build-with-claude/streaming), [Microsoft IChatClient](https://learn.microsoft.com/en-us/dotnet/ai/ichatclient).
